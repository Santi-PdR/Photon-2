# Photon 26.2.2.3 Reference API Map

This is a behavior/API inventory from the user-supplied `photon-neoforge-26.2-26.2.2.3.jar` and the official `26.2` source branch at commit `8232cb4` (2026-09-25, mod version `26.2.2.3`) cloned privately under `/tmp/photon-upstream-26.2`. CFR 0.152 also generated 423 readable Java files for comparison. Neither upstream checkout nor decompiler output is copied wholesale into this repository. These notes identify migration work and are not a claim that any Photon subsystem is ported.

## Forge baseline comparison

- The working tree now uses a community Photon 2.2.6.a Forge 1.20.1 baseline (380 Java files) with LDLib2 2.2.39.a and KilaGraph 20.1.0.14 Forge artifacts under `libs/`.
- The official 26.2 source has 419 Java files. Path comparison finds 344 shared paths, 75 source paths added or renamed in 26.2, and 36 Forge-baseline paths absent from 26.2. Most importantly, 26.2 replaces the old `client/gameobject/emitter/renderpipeline` design with 52 classes under `client/render` and updates client event hooks to render-pipeline/frame-graph APIs unavailable in Forge 1.20.1.
- The Forge project compiles with Java 17 against the declared Modrinth Embeddium/Oculus artifacts with the Iris bridge and mixins included; `processResources jar --offline` and `reobfJar` also succeed. The reobfuscated JAR contains the bridge, metadata, assets, and packaged license. Soft-particle fade is in the existing material/GLSL path. The legacy Forge pass preserves 26.2's distance-sort behavior for independent translucent primitives with a stable packed-key path when sorting from the origin, while other sorter functions keep the general implementation. Revision-aware CPU dynamic meshes feed both model render paths. Standalone JSON models bake from the active resource manager with parent resolution, without standalone model registration. Mesh sampling keeps source topology beside render quads: JSON stays unwelded, OBJ keys vertices by v/vt/vn, and glTF preserves source vertex indices per primitive instance; animated poses refresh sampling positions in place. The animated glTF source reads sparse accessors and relative buffers as well as skin weights, skeleton hierarchy, inverse-bind matrices and embedded TRS clips; it shares same-frame CPU poses across emitters, calculates tangents lazily, retargets animation-only glTF files by joint name, supports rigid animated nodes, exposes clip selection and external-file picking, and bakes per-particle phases for CPU and instanced VAT texture-buffer rendering. Shader compilation and runtime appearance are not verified; GPU skinning beyond VAT and the Forge runtime path for FX Packs remain to be checked.
- The FX runtime now has the 26.2 transient global playback-rate API. It applies the selected rate to the root particle simulation and the timeline master clock; fractional clock values and rate-scaled frame interpolation keep particle, timeline, and rendered animation time aligned. NaN and infinite inputs fall back to normal speed, and negative rates clamp to zero. This compiles, but has not been exercised in a Forge client.
- Forge custom shader materials now expose the 26.2 `U_DepthParams` contract in forward-Z form: depth-to-NDC `(2, -1)` plus near/far distances unprojected from the current projection matrix. JUnit tests cover perspective and orthographic projection ranges; runtime execution of a custom shader reading this value remains to be checked.
- Forge custom shader materials now expose the 26.2 `setUniformValue` / `getUniformValue` API for user-defined uniforms, persist override values in additional NBT, and reapply them to the selected LDLib2 shader variant on draw. Engine-owned `U_*` uniforms remain protected. This is compile/client-startup verified only; invoking the setter and a save/load cycle still need an editor/runtime fixture.
- Animated glTF sources now expose 26.2's `hasAnimation`, `getClipNames`, `asDynamic`, and nullable `pinClock(seconds)` behavior. The pinned clock feeds the same clip-time calculation as the editor/world clock, and VAT sources report no CPU dynamic provider. Build and client startup pass; imported animation playback and deterministic clock behavior still need an in-client asset fixture.
- The timeline transport bar now follows the 26.2 icon layout and supplies play/pause, stop-to-start, one-tick stepping, and jump-to-content-end actions. Six matching icons and localized English/Chinese tooltips are included. It compiles, but has not been checked visually in a Forge client.
- Timeline ruler labels now use the 26.2 fit check so a tick number is omitted if its text would cross either horizontal ruler boundary. The fit geometry is isolated as pure code and covered by a boundary unit test; visual rendering remains runtime-unverified.
- Editor shortcuts now use Forge `KeyMapping`s registered in Minecraft Controls, covering Q/W/E/R gizmo modes, X gizmo space, Z draw mode, B bloom, Space/Shift+Space playback, comma/period stepping and Ctrl+R replay. The 26.2 `PhotonEditorActions` IDs and Scene/Playback category names are exposed using Forge `ResourceLocation`. TextField editing and right-button camera flight guard the scene shortcuts. Labels are localized in English and Chinese; runtime focus behavior remains unchecked.
- Key mapping names and their separate Scene/Playback categories now match 26.2's public keymap identifiers. A key-by-key locale comparison found no missing 26.2 English or Chinese entries.
- The Forge client now registers a mod-list configuration screen corresponding to 26.2's config extension, with every current setting exposed through toggles, translated enum selectors and sliders, existing localized descriptions, and save-on-change. Client startup succeeds with the extension registered; opening the screen and persistence across restart remain to be verified.
- The Forge post-FX target pool now treats allocation failure like 26.2: it logs and remembers each failed size/format, returns no target, and clears failed-shape memory on pool invalidation. Graph execution, mask mixing, and standalone post-FX skip or degrade the current chain safely. Free-target byte accounting is incremental, and stale/budget eviction pops the oldest target from each size bucket rather than rescanning, sorting, and searching the entire pool. Compilation passes; GPU failure behavior has not been induced in a client.
- FX Pack export metadata now declares `pack_format: 15`, aligned with the repository's Minecraft 1.20.1 resource-pack metadata; the 26.2-era `34` value has been removed. The target-format string is present in the reobfuscated JAR. A generated pack has not been loaded in Minecraft.
- Animated glTF sources persist external animation paths in the 26.2 `animationFiles` string-list NBT shape and read legacy-configured comma-separated values for compatibility. Codec tests cover list round-tripping, malformed resource IDs and an absent field; editor save/load remains runtime-unverified.
- The reference `photon:engine.glsl` include is now present for Forge custom shaders. It exposes camera/viewport/inverse-projection uniforms and the `photon_ndc_depth` / `photon_eye_depth` helpers, with `U_DepthParams` adapted to Minecraft 1.20.1 forward-Z. The existing matrix and depth parameter tests cover the supporting projection conversion; shader-include compilation and visual output remain unverified without a client session.
- Custom post-FX shader passes now receive the captured render camera's `U_InverseProjectionMatrix`, `U_InverseViewMatrix`, `U_CameraPosition`, and projection-derived `U_DepthParams`. The pass introspector treats these as engine-managed rather than exposing them as editable graph ports; a pure parser test covers that contract. Visual shader output remains unchecked.
- OBJ/glTF mesh-sampling identity now has synthetic parser fixtures covering shared vertices and per-primitive separation; real resource-pack asset sampling, animated-model playback, and VAT remain unchecked. Continue reconciling the 26.2 renderer, post-FX and FX Pack behavior, and validate data roundtrips. Client startup reached Photon shader compilation and atlas creation without GLSL errors; absent soft-particle uniform/sampler warnings are resolved. Dedicated-server startup remains runtime-unverified; static proxy selection now uses the Forge side gate.

## Startup, sides, and configuration

- `Photon` is the mod entrypoint (`photon`). It initializes common infrastructure, then selects the client or common/server proxy factory through `DistExecutor.safeRunForDist`. The reobfuscated entrypoint bytecode has no direct `new PhotonClientProxy` instruction in its common constructor.
- The client registers client configuration and a config screen; the common/server factory initializes only common registries, command argument types, and networking. `Photon.isUsingShaderPack()` calls the Iris bridge through Forge `DistExecutor.safeCallWhenOn`, so shared code keeps that client-only access behind a physical-side gate. The build verifies these common classes, but dedicated-server runtime classloading still lacks a live check because the previous run stopped at the EULA preflight.
- The config currently has 11 entries covering bloom, Iris compositing, FX compositing, custom effects, and post-FX memory budget.
- The common proxy registers two command-argument types, networking registration, and Photon registry initialization.

## Registries and content model

Six Photon registries are initialized through LDLib2: FX object types, materials, number functions, shapes, model sources, timeline tracks, and animated properties. Several use LDLib2 annotations and classpath scanning rather than vanilla block/item registries. An equivalent Forge 1.20.1 implementation must preserve stable string IDs and registration order while replacing any incompatible LDLib2 APIs.

## Commands and networking

- Server command tree: `/photon fx <location> block|entity ...` and `/photon remove block|entity ...`; client commands are registered separately.
- Four packet types are registered for client playback/removal: block effect, entity effect, remove block effect, and remove entity effect. The inspected packet registrar sends these to clients; handlers then resolve FX data and create/stop client runtimes. No C2S Photon payload is registered by the inspected network class.
- The 26.2 reference uses NeoForge `RegisterPayloadHandlersEvent`, `CustomPacketPayload`, `StreamCodec`, and `PacketDistributor`.
- The Forge 1.20.1 port now uses a versioned `SimpleChannel`, explicit message IDs, `FriendlyByteBuf` encode/decode, and side-aware handlers. All four S2C payloads have been compared field-by-field with the reference; multiplayer delivery, malformed-payload handling, and dedicated-server classloading remain runtime-unverified. Forge's SimpleImpl supports client, tracking-chunk, and all-player sends.
- The registered entity auto-rotation argument now uses common `AutoRotateMode`; the client-facing `EntityEffectExecutor.AutoRotate` and constructor remain available, mapped by enum name. Tests lock the shared ordinal order and S2C round trip. `javap` confirms the registered command argument class no longer references the client executor; no dedicated-server process was launched.

## Client runtime, resources, and rendering

- Client startup registers render pipelines and particle groups; adds FX Pack resource repositories; and installs mesh, FX, shader, and post-FX reload listeners.
- Frame and level events drive material/post-FX previews, post-FX composition, world-state cleanup, opaque depth capture, Iris interop, and GUI overlays.
- The supplied JAR has 311 `client/gameobject` classes, 71 FX/runtime classes, 92 render classes, 77 post-FX classes, 16 shader-graph classes, 75 editor classes, and 26 UI test/scenario classes.
- The current client event path references `RegisterRenderPipelinesEvent`, `FrameGraphSetupEvent`, `RenderFrameEvent`, and newer render-state camera objects. Forge 1.20.1 has no direct API-equivalent for the whole 26.2 render graph path; it needs a separately designed render-stage/frame lifecycle using 1.20.1 events, render targets, and targeted mixins.
- The JAR declares a required Mixin plugin and client mixins for particle engine, shader manager, global shader uniforms, and Iris internals. These are high-risk API seams requiring individual compatibility checks.

## Java and Minecraft API deltas

| Reference API (26.2 / NeoForge) | Forge 1.20.1 migration direction |
|---|---|
| Java 25 classfiles (major 69) | Recompile source for Java 17; do not load/reference the supplied bytecode as a runtime dependency |
| `net.minecraft.resources.Identifier` | `ResourceLocation` |
| `RegisterPayloadHandlersEvent` + `StreamCodec` custom payloads | Forge `SimpleChannel` messages with `FriendlyByteBuf` codecs and explicit protocol version |
| NeoForge `DeferredRegister` / event packages | Forge 47 registries and event-bus packages |
| New render-pipeline/frame-graph events and render-state camera | Rebuild against Forge 1.20.1 render stages and rendering APIs; use narrowly scoped mixins where Forge events cannot preserve behavior |
| New command permission-check API and identifier argument types | Brigadier/Forge 1.20.1 command APIs and argument registration |

The Forge networking direction is based on the [Forge 1.20.x networking guide](https://docs.minecraftforge.net/en/1.20.x/networking/); client-only particle provider registration is documented as client-sided in the [Forge particle guide](https://docs.minecraftforge.net/en/1.20.1/gameeffects/particles/).

## Dependencies

The reference metadata requires NeoForge 26.2+, Minecraft 26.2, LDLib2 `[26.2.2.41.a,)`, and KilaGraph `[26.2.0.15,)`; KilaGraph 26.2.0.15 is jar-in-jar. These exact dependency lines cannot satisfy the Forge 47 / Java 17 target. The Forge branch uses LDLib2 2.2.39.a and KilaGraph 20.1.0.14 from `libs/`, declares Embeddium/Oculus as optional client-render APIs, and now declares KotlinForForge 4.10.0 because LDLib2 contains Kotlin-compiled classes without the Kotlin runtime. Gradle resolves KFF from its official Maven repository, and `mods.toml` requires mod ID `kotlinforforge` version `[4.10,)` on both sides. The final JAR has passed local Java 17 build/test, metadata inspection, and the GitHub Actions artifact check. Library behavior in a live client/server remains unverified; see `PORT_AUDIT.md` for the current evidence.
